ESP-NOW remote shutoff

A second ESP32 sends a raw uint8_t: nonzero -> conveyor OFF, zero -> conveyor ON.

The receive callback (onDataReceived) runs in the Wi-Fi stack's own task context, so it does no stepper work itself — it stores the byte in latestRemoteValue and gives remoteDataSemaphore, which RemoteShutoffTask blocks on. A semaphore only signals "something's ready," it doesn't carry a value the way a task notification does, so the byte itself has to travel through a separate shared variable. The actual on/off still goes through sendStepperCommand(), the same entry point BLE uses, so StepperControlTask remains the only thing that ever touches the timer directly.

Detailed Description

Direct-register stepper motor driver for the sorting conveyor belt, with BLE and ESP-NOW command inputs routed through FreeRTOS.

Date
08/19/2026
Version
1.0
Author
Sadriyah Farah, Valentina Aguilar-Hernandez

A 28BYJ-48 stepper (driven through a ULN2003 module) is stepped from a hardware timer ISR using direct GPIO register writes instead of digitalWrite(). All stepper state (on/off, speed, direction) is owned exclusively by StepperControlTask; every other input source — the BLE characteristic's write callback and the ESP-NOW receive callback — only ever calls sendStepperCommand(), which pushes into stepperCommandQueue. This keeps BLE and ESP-NOW, which each run in their own task/callback context, from racing each other over the timer or the direction variable.

Input sources:

  • BLE: opcode byte(s) written to CHARACTERISTIC_UUID. See the protocol table above sendStepperCommand()'s BLE callback (MyCallbacks) below.
  • ESP-NOW: a single uint8_t from a second ESP32. Nonzero turns the conveyor off; zero turns it back on. Delivered to RemoteShutoffTask via a binary semaphore (plus a shared byte carrying the value, since a semaphore alone can't), not the command queue directly, since the ESP-NOW receive callback should do as little work as possible before returning.

Function Documentation

◆ applyStep()

void IRAM_ATTR applyStep ( uint8_t pattern)

Writes one step pattern to the coil pins using direct register access.

Bit-masks each coil's target state into one combined set-mask and one combined clear-mask, then writes both in a single instruction each via the GPIO peripheral's write-1-to-set/write-1-to-clear shadow registers (GPIO.out_w1ts / GPIO.out_w1tc). Writing a 1 to a bit sets/clears that GPIO and leaves every other pin's output level untouched, so no read-modify-write is needed — this is ISR-safe and far cheaper than digitalWrite(), which looks the pin up in a table and does validation/locking on every call.

Parameters
pattern4-bit coil pattern (bit0=IN1 ... bit3=IN4) from stepSequence

◆ latestRemoteValue

volatile uint8_t latestRemoteValue = 0

Most recent byte received over ESP-NOW.

Note
Written by onDataReceived, read by RemoteShutoffTask. Safe without a mutex: a single-byte write is atomic on this architecture, and remoteDataSemaphore already enforces a strict write-then-signal / wait-then-read handoff between the two, so there's no window where the reader could see a half-written value.

◆ stepperCommandQueue

QueueHandle_t stepperCommandQueue = NULL

Queue of pending StepperCommand entries.

One task (StepperControlTask) owns all stepper state (on/off, speed). Everything else — BLE, ESP-NOW, or any future input source — only ever sends a command into this queue. Nothing outside StepperControlTask calls setStepRateHz() directly, so there's no race between two input sources fighting over the timer at once.
